# Security and Privacy Baseline

The delivered foundation provides BCrypt password hashes, signed short-lived JWT access tokens, method/request authorization, input validation, CORS allowlisting, correlation IDs, masked errors, and append-only audit writes. Secrets come from environment variables.

Phase 6 adds object-level medical-record rules. A patient principal resolves to exactly one patient and can read/upload/download only that patient's records. A clinician must use an account explicitly linked to one active doctor; patient access requires an actual appointment care relationship, and visit creation additionally requires that the doctor owns the appointment and the appointment is in consultation or completed. Sensitive reads, writes, uploads, and downloads emit audits that identify the resource and outcome without duplicating clinical content.

Phase 7 derives one patient ID from the authenticated principal and includes it in the chunk database query before ranking. Conversation lookup also requires both conversation ID and patient ID, returning not-found rather than revealing another patient's thread. The local grounded mode performs no external medical-data sharing. Questions, answers, report text, and diagnoses are excluded from audit payloads. Medical-safety preflight runs before extraction/retrieval, and in-memory per-user throttling limits development abuse; production requires a distributed limiter and formal model/OCR governance.

Phase 8 diagnostic reads resolve the patient from the JWT and query orders by that patient ID. Scheduling and cancellation lock the owned order before changing capacity. Clinician ordering requires the linked doctor to own the source appointment and the appointment to be in consultation or completed. Diagnostic processing and result verification require a diagnostic staff role, and only an atomically verified result is returned as final patient evidence. Result text and values are excluded from audit payloads. Production must additionally bind diagnostic staff grants to an explicit hospital assignment before multi-hospital deployment.

Phase 9 patient request history resolves the patient from the JWT and queries only that patient ID. Only clinician/blood-bank roles can create a request, and a linked doctor is restricted to their hospital; an optional appointment must match patient, hospital, and doctor. Batch updates, worklists, repeat search, fulfilment, and donor matching require blood-bank/admin roles. Inventory reservation uses database row locks and never considers quarantined, expired, or stale verification. Public/patient availability omits batch references and verifier identities. Donor contacts appear only to blood-bank staff after explicit consent, staff eligibility verification, exact group match, and a documented inventory shortfall. Production must additionally bind staff grants to hospital assignments, require MFA, and route donor contacts through an audited private notification workflow.

Phase 10 ambulance history derives the patient from the JWT and queries only that patient ID. Patient creation records a request but cannot assign a vehicle or advance dispatch state. Assignment locks both request and ambulance, requires an available active vehicle from the same hospital, and is restricted with acknowledgement/status/location actions to dispatcher/admin roles. Patient DTOs expose only call sign, registration, coarse area, and update time; exact coordinates and crew contact stay in the privileged fleet API. Audit entries contain identifiers and action names, never pickup addresses, contact numbers, notes, coordinates, or crew contact. Production additionally requires hospital-scoped dispatcher grants, MFA, signed device telemetry, stale-location handling, emergency-provider governance, and formal crew identity/device enrollment.

Phase 11 recovery lists derive the patient from the JWT and verify case ownership again under a pessimistic lock before accepting a decision. A doctor cancellation creates a prompt but does not change the appointment. Rescheduling uses the transactional appointment/capacity ledger, and refund selection is explicitly a review state. Linked doctor accounts can update and view only their own doctor queue. Reception, cashier, and admin roles are separated at the API and UI; however, non-doctor hospital assignment is still a development boundary and must be replaced with tenant-scoped staff grants plus MFA before production. Notification-failure totals are super-admin only, patient identifiers on staff queues are private patient numbers rather than names, and free-text operational reasons must not contain diagnosis details.

Phase 12 accepts only server-decoded JPG/PNG content after magic-byte, byte-size, minimum-dimension, and pixel-count validation. Images use opaque private storage keys and are served with `no-store` only after patient ownership or reviewer-role authorization; paths and hashes are not exposed. Patient lists are ID-derived, staff mutations lock the analysis row, reaction observations are single-write, and the observer cannot verify their own work. The development analyzer explicitly returns `NOT_CONFIGURED`. Production requires validated model governance, encrypted object storage, malware scanning, tenant-scoped staff grants, MFA, LIMS confirmation, purpose/consent records, retention/deletion policy, watermark-safe review, and clinical approval.

Uploaded reports are limited to 10 MB and accepted only when server-side magic-byte detection confirms PDF, JPEG, or PNG. Names are sanitized, content is SHA-256 hashed, and bytes are stored using opaque keys outside the web root. Downloads pass through authorization and return `Cache-Control: no-store`; storage paths are never exposed as public URLs. The local filesystem implementation is a development adapter behind a storage interface, with a Docker named volume for persistence.

Before production rollout, add refresh-token rotation/revocation, provider-managed key rotation, rate limiting, hospital-scoped staff grants, MFA for privileged roles, consent workflows, managed private object storage, malware/content scanning, encryption-at-rest key governance, backup restoration drills, security headers at the edge, and jurisdiction-specific retention configuration.

Authorization must be enforced in services using both principal and resource scope. Knowing a UUID never grants access. Audit payloads describe actions without copying clinical content. Emergency override access must be time-limited, reasoned, reviewed, and clearly audited.
